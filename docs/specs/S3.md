## 1. Migración v7 en `src/db/migrate.ts`

La última migración es la **6**. Agregá un `SchemaMigrationStep` con `version: 7`,
`name: 'plan-items'`, siguiendo el patrón exacto de las existentes
(`precondition` / `apply` / `postcondition`, cada una verificable por separado).

```sql
CREATE TABLE plan_items (
  id          TEXT PRIMARY KEY,               -- 'S.3', 'R.6', 'H.10.2'
  sprint      TEXT NOT NULL,                  -- encabezado ## del bloque
  block       TEXT,                           -- sub-bloque, puede ser NULL
  delegation  TEXT NOT NULL CHECK(delegation IN ('🧠','⚡','🔍')),
  title       TEXT NOT NULL,
  body        TEXT NOT NULL DEFAULT '',       -- la prosa/evidencia del ítem, literal
  status      TEXT NOT NULL CHECK(status IN ('open','done')),
  commit_sha  TEXT,
  closed_at   TEXT,
  position    INTEGER NOT NULL,               -- orden dentro del sprint, para el render
  CHECK (status = 'open' OR commit_sha IS NOT NULL)
);
CREATE INDEX idx_plan_items_status ON plan_items(status, sprint);

CREATE TABLE plan_item_deps (
  item_id    TEXT NOT NULL REFERENCES plan_items(id) ON DELETE CASCADE,
  depends_on TEXT NOT NULL REFERENCES plan_items(id) ON DELETE RESTRICT,
  PRIMARY KEY (item_id, depends_on),
  CHECK (item_id <> depends_on)
);
```

**El `CHECK` de `commit_sha` es el punto entero del ítem.** Es lo que impide que un LLM cierre
trabajo escribiendo prosa: para pasar a `done` tiene que existir el commit. No lo relajes, no lo
conviertas en advertencia, no lo muevas a la capa de aplicación. Si un ítem histórico no tiene
commit conocido, se importa con el sha del commit que lo marcó `[x]` (`git log -S`), y si no se
puede determinar, con el sha del commit de la importación misma — nunca con NULL.

`scope[]` NO se modela todavía: el scope-lock vive en `.orchestos/active-item.json` y unificarlo
es otro ítem. No lo agregues.

## 3. Importación única desde PLAN.md

Script `scripts/plan-import.ts`. **Reutilizá `parsePlanFeatureStatus()` de
`scripts/plan-status.ts`** — ya resuelve el regex de ítems, el sprint y el bloque; no escribas un
parser nuevo. Lo que hay que agregar es la captura del **cuerpo** (las líneas indentadas que
siguen a cada ítem, hasta el próximo ítem o el próximo `##`) y el `position`.

Tras S.2, la mayoría de los ítems cerrados tienen el cuerpo en `docs/done/*.md`: el import debe
seguir el enlace `→ [evidencia](...)` y traer ese texto al campo `body`. Un ítem cerrado cuyo
`body` quede vacío es un error, no un caso válido.

`depends_on` no existe en PLAN.md como dato. Para esta importación: **dejar `plan_item_deps`
vacío**. Poblarla es trabajo manual posterior de Carlos sobre el board (S.6); no inventes
dependencias leyendo frases como "Orden de ataque propuesto: R.1 → R.2".

## 4. Gate de fidelidad (el criterio de aceptación real)

El import es correcto si y solo si se demuestra que **la DB contiene lo mismo que PLAN.md**:
- Mismo conjunto de IDs, mismo `status` por ID, comparado contra
  `.orchestos/feature-status.json` generado antes de tocar nada. Diferencia esperada: cero.
- Conteo: `SELECT COUNT(*) FROM plan_items` == ítems que `plan:status` detecta hoy.
- Para 3 ítems (uno abierto, uno cerrado con evidencia larga, uno con sub-bloque), pegar el
  `body` guardado y confirmar que coincide con el archivo de origen.
- Un test que compruebe que el `CHECK` funciona: intentar `INSERT` de un `done` sin `commit_sha`
  debe fallar. Sin ese test, el ítem no está hecho.

Tests en el estilo del repo: inyección de dependencias, nunca `mock.module()`
(ver memoria `reference-bun-mock-module-gotcha`), y `ORCHESTOS_HOME` limpio — los tests no deben
escribir en la DB real (ver `reference-test-fixtures-leak-into-real-db`).
