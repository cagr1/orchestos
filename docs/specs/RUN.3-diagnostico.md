# RUN.3 — diagnóstico (analizar, gpt-6.1-sol, 2026-11-27)

**Resumen: no hay un contrato terminal uniforme.** Chat sí persiste finales; tareas mezcla espera y lanzamiento terminado en `pending`; los gates usan señales distintas. RUN.3 pide precisamente este diagnóstico (`PLAN.md:354`; `src/db/chat-turns.ts:6`; `src/cli.ts:1356`).
1. **Chat**
- `POST /api/chat` responde al terminar el turno: espera `runTurn`, resuelve la propuesta de tarea y persiste éxito antes de devolver JSON; `appendLiveText` publica avances por separado, no adelanta la respuesta HTTP (`src/dashboard/handlers/chat.ts:1938`, `:1960`, `:1965`, `:1983`).
- Terminar el turno no implica terminar la tarea creada: esta se lanza como otro proceso (`src/dashboard/handlers/tasks.ts:385`, `:397`).
- La DB distingue `pending`, `completed`, `failed`, `interrupted`, `cancelled`; `/timeline` expone `id`, `status`, `error` y un `pending` agregado (`src/db/chat-turns.ts:6`; `src/dashboard/handlers/chat-sessions.ts:450`, `:486`).
- Éxito devuelve texto; fallo del CLI devuelve HTTP 502 con `error/notice` y persiste `failed`; timeout usa ese fallo clasificado, no un evento terminal propio (`src/dashboard/handlers/chat.ts:1983`, `:1347`; `scripts/ui-gate/flows/chat-timeout.mjs:51`).
- Abort por Stop persiste `cancelled` y devuelve `stopped:true`; interrupción devuelve `interrupted:true`; `/stop` puede responder antes con `202 stopping` (`src/dashboard/handlers/chat.ts:2256`, `:2263`; `src/dashboard/handlers/chat-sessions.ts:708`).
- **Hay una inconsistencia concreta:** `/turn-status` convierte `completed` en `none`, pero no contempla `cancelled`: este cae en `pending` mientras su lease siga vigente, después en `interrupted` (`src/dashboard/handlers/chat-sessions.ts:584`, `:593`; `src/db/chat-turns.ts:230`).
- Reinicio ordenado marca `interrupted` y aborta; recuperación al arrancar marca únicamente leases vencidos. Un proceso muerto puede dejar temporalmente `pending`, sin respuesta HTTP final (`src/dashboard/handlers/chat-turn-registry.ts:13`; `src/db/chat-turns.ts:301`; `src/dashboard/server.ts:921`).
- La persistencia de fallo es *best effort*: si falla la escritura, se devuelve el error igualmente; por tanto, tampoco está garantizada la marca durable en ese caso (`src/dashboard/handlers/chat.ts:1302`, `:1312`, `:2247`).
- En DOM encontré indicador de trabajo, avisos clasificados y “Respuesta detenida”; no encontré un atributo terminal común correlacionado por turno. `div.prose` sirve también para texto vivo (`src/dashboard/app/src/components/thread/ThreadThinking.tsx:26`, `:32`; `src/dashboard/app/src/components/thread/StoppedResponse.tsx:2`; `src/dashboard/app/src/components/chat/OrchestChatView.tsx:692`).
2. **Tareas**
- `tasks.yaml` admite además `blocked`; `runs.status` solo `done|blocked|failed`: son vocabularios diferentes, sin terminal común (`src/tasks/schema.ts:13`; `src/db/runs.ts:81`).
- USO.49 reintenta dentro del mismo lanzamiento: escribe `pending`, incrementa contador y vuelve a ejecutar mientras el resultado sea `retry`; ese `pending` es transitorio (`src/cli.ts:1343`, `:1417`).
- **Sí: `pending` también significa lanzamiento terminado sin éxito**, por presupuesto insuficiente; devuelve `blocked` al controlador conservando `pending` en YAML (`src/cli.ts:1356`).
- Árbol sucio también se considera terminal aunque siga `pending`; el reconciliador necesita motivo y vida del proceso para decidir, y puede cerrar el seguimiento sin cambiar ese estado (`src/dashboard/handlers/task-run-reconcile.ts:91`, `:104`, `:112`).
- Un run fallido tampoco prueba agotamiento de la tarea: QA registra el intento fallido y puede devolver `retry`; el reporte verifica conjuntamente YAML y run para declarar éxito (`src/run/harness.ts:997`, `:1029`; `src/dashboard/handlers/task-report.ts:100`).
